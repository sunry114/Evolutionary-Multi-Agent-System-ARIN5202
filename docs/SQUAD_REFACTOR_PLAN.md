# Squad 分支重构计划

目标场景：用户提交一次目标，把工单交给一名 agent 或一个 Squad；打开同一张工单，就能看到谁负责、为何改派、当前阻塞、产物以及谁需要采取下一步行动。首版采用单工作区、一个可配置 Squad（队长也是成员）、本地 SQLite 和现有串行执行器。多租户、定时自动化、远程 daemon 和多厂商 CLI 适配留待后续需求决定。

产品参照采用 Multica 的工单指派、队长路由和运行记录。课程同时要求群组自主拆解、角色协商、成员间委派、人机私聊和群聊、关键操作审批、私有记忆与隔离。团队继续使用课程指定的 DeepSeek/HKGAI、已有搜索/文件/代码/Git 工具及完成率和耗时评测。课程文档类验收示例使用 Markdown 或 TXT。[Multica 产品说明](https://github.com/multica-ai/multica#build-the-team)。课程原文见本地提供的 `project.txt`。

## 分阶段交付

| 阶段 | 改动 | 完成条件 |
|---|---|---|
| 1 · 工单与 Squad | 扩展角色配置，记录队长和成员。根任务增加目标接收方（agent 或 Squad）；与执行子任务的 owner 分开。把角色、队长和路由模式快照写入本次运行。先交付 CLI 建单、列表、详情、显式启动。 | 未配置模型也能建单，启动沿用原工单 ID。已有角色配置可继续读，旧任务可查看和按原配置恢复。重复启动不会产生第二次执行。若新增表或字段，提交增量迁移、旧库升级测试，并更新 CI 中固定的 schema 版本检查。 |
| 2 · 队长分派与协商 | Squad 模式由队长调用 Planner，逐项提名。成员可接受、调整范围、推荐同伴或报告阻塞；队长处理反建议，新负责人确认后才执行。直接指派模式由指定成员接单，复杂任务仍可委派。每轮记录发起者、对象、理由与最终职责，设置轮次上限。先让 squad 与 bidding 两种模式可显式选择。 | 在同一脚本案例中证明一次直接接受、一次反提议真正改变 owner 或执行描述、一次协商耗尽产生可解释的阻塞。调整范围时保留用户验收条件；超出目标时沿用澄清流程。 |
| 3 · 成员委派与恢复 | 成员通过现有工具自行发起子任务，复用接单协议、预算和产物交换；父任务取得结果后再整合。为委派请求和恢复操作保存稳定标识，在事务中检查预期状态。 | 端到端证明发起人是执行成员。孙任务等待人审批时，根工单显示阻塞原因；同意或拒绝后沿原链恢复，重复提交也只产生一次副作用。依赖失败和拒绝能传回根工单。 |
| 4 · 工单工作台 | 在现有 Web 中提供工单列表、详情和负责人入口。详情聚合同一任务树的协商、评论、日志、产物、审批、审查和修订。展示下一步动作，由 CLI/Web 共用相同应用操作。 | 浏览器完成建单、交给 Squad、查看改派理由、批准、审查退回、运行修订、接受交付。另一张工单的聊天或审批不会出现在本单。 |
| 5 · 切换默认路由 | 新工单默认 squad，旧运行缺少路由标记时继续按旧格式处理。成员在协商和执行时使用个人经验，沿用记忆关闭开关。将竞标保留为对照；后续是否删除由历史恢复需求和评测决定。 | 用同一模型、数据集、验收条件、审批策略比较两种路由的目标/子任务完成率、耗时、路由调用数和失败原因。用连续的相关任务验证经验能跨任务被检索；现有评测按案例创建临时目录，跨任务实验需显式复用同一组记忆，并让对照组从相同初始状态开始。 |

## 首个演示用例

用户要求「从提供的测试日志生成故障分析和复核结论」。队长提名分析员撰写；分析员提出只负责根因分析，由验证员独立复核。队长接受后，分析员主动向验证员发出子任务，验证员接受并返回证据。分析员汇总为 report.md，用户在工单里审查。用固定响应的测试替身核验协商前后职责、委派发起人、产物及审查记录，再用真实模型运行相同场景，分别记录结果。

建议第一批改动只交付阶段 1 的纵向路径：配置一个 Squad，在 CLI 建立指派给它的工单，再用原执行器启动并按工单 ID 查看结果。下一批单独引入协商，便于定位工单生命周期和分派策略各自引入的回归。
